# DR: 跨 Workspace 与 steer 投递前的用户确认预览

Status: rejected — 单用户本地交接均可事后纠正且无越界风险，事前确认的打断成本高于其拦截收益

## Problem

交接正文由模型组织，用户在消息发出前看不到最终文本。跨 Workspace 投递与 `steer` 打断两类操作影响更大：选错目标、用错模式或正文跑偏时，消息已经投出。需要一个让用户在实际准入前看到目标身份、模式与完整正文并决定是否放行的机制。

## Proposal

复用宿主 `tools/pre-execute` 审批入口（允许 / 拒绝 / 取消，决定写入审计）：`session_send` 在跨 Workspace 或 `mode=steer` 时先展示确认卡片（目标 ID + 标题 + 工作区目录、模式、回报选项、完整正文），用户允许后才真正投递；拒绝时模型收到明确拒绝信号并调整。同 Workspace 的 `queue` 投递不触发，保持直发。`session_read` 的显式授权策略可作同方向后续。

交互原型见本地 demo（docs/demo-dispatch-preview.html，未入库）。

重启条件（满足其一再重新评估）：工作区之间出现敏感性边界（公司 / 客户 / 私人项目混用）；接入定时投递等无人值守发送；宿主启用多用户或远程访问 principal。

## Alternatives considered

- **仅靠事后回执展示正文** —— 工具结果与回执已可看到所发正文，缺的只是事前否决权；在可纠正的单用户场景里，事后可见已覆盖大部分需求。
- **缩小触发范围到仅 steer** —— steer 实际语义是下一步接入而非掐断工作，代价低于预期，单独为它设门收益更小。
- **配置开关默认关闭** —— 保留代码路径但默认直发：功能本体收益不足时，维护一条默认关闭的路径只是负担。

## Acceptance criteria

- 确认后只投递一次，目标 ID、正文、模式与预览一致；拒绝或取消时无投递。
- 目标在确认后被归档或失去访问权时，准入给出明确反馈。
- 决定写入宿主审计；缺少审批服务的部署按拒绝处理。

## Risks

- 每次符合条件的投递都打断用户流程；触发频率与错误率双低时净体验为负。
- 审批依赖宿主 `tools/pre-execute` 的可用性与 profile 装配，未装配时行为需要降级定义。
